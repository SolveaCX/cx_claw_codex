# 售后工单

所有创建动作都遵循“先确认后提交”：先向用户展示整理后的工单明细，获得明确确认后才能调用创建接口。

## CLI 入口

工单创建、列表查询、详情查询、追加消息，继续通过本 skill 的 CLI 调用 GPT support API：

```bash
node "<PLUGIN_ROOT>/plugin-cli.mjs" support <command> --pretty
```

可用命令：

```bash
# 创建工单（基本）
node "<PLUGIN_ROOT>/plugin-cli.mjs" support create-ticket \
  --content "<问题描述>" \
  --brand "<brand，可选>" \
  --issue-type "<工单类型 code，见下方问题分类表>" \
  --ext '<{"chatId":"<chatId>"}>' \
  --subject "<工单标题，可选>" \
  --contact-email "<邮箱，可选>" \
  --pretty

# 创建工单（带附件，可重复 --attachment）
node "<PLUGIN_ROOT>/plugin-cli.mjs" support create-ticket \
  --content "<问题描述>" \
  --issue-type "<工单类型 code>" \
  --attachment "<沙箱内文件路径>" \
  --attachment "<另一个文件路径（可选）>" \
  --pretty

# 分页查询工单列表
node "<PLUGIN_ROOT>/plugin-cli.mjs" support list-tickets \
  --page 1 \
  --page-size 20 \
  --pretty

# 查询工单详情和消息
node "<PLUGIN_ROOT>/plugin-cli.mjs" support get-ticket \
  --ticket-number "<工单号>" \
  --pretty

# 追加客户消息
node "<PLUGIN_ROOT>/plugin-cli.mjs" support append-message \
  --ticket-number "<工单号>" \
  --content "<用户补充描述>" \
  --pretty
```

## 提交工单信息

创建工单前尽量整理以下信息：

| 字段 | 说明 |
|---|---|
| 问题描述 | 用户遇到的问题、期望结果、实际结果 |
| 问题分类 | 见下方「问题分类」表，选对应 code |
| 扩展字段 | 按分类填写必要字段（见下方「按分类必填」） |
| 附件 | 用户提供的截图/日志等文件，通过 `--attachment` 上传 |
| 来源信息 | 当前会话或页面上下文中可用的 sourceType/sourceId |
| 品牌 | 如果上下文能拿到 brand 则带上；拿不到不要让用户反复补 |
| 联系邮箱 | 可选，用于后续通知 |

### 问题描述：使用纯文本

`--content` 里的工单描述使用纯文本，不使用 Markdown 标题、列表、表格或 HTML。内容要准确、精准、客观，方便客服和研发直接阅读、定位和复制处理。建议包含：

- 问题现象
- 期望结果和实际结果
- 已尝试的排查步骤
- 相关 ID、时间点、截图或日志说明

不要写 `# 标题`、`- 列表项`、Markdown 表格、HTML 标签或 `\n` 这种字面量转义。需要分段时，直接使用正常换行。

### 问题分类

| code | 中文含义 |
|---|---|
| `agent_badcase` | AI 客服异常/Bug |
| `consult` | 产品咨询 |
| `agent_feature` | AI 客服功能需求 |
| `integration_feature` | 集成需求 |
| `ticket_feature` | 工单功能需求 |
| `ticket_bug` | 工单 Bug |
| `other` | 其他 |

### 按分类必填（放 `--ext`）

| 分类 code | 必填 ext 字段 | 说明 |
|---|---|---|
| `agent_badcase` | `chatId` | 异常对话的 Chat ID，用于定位问题 |
| `ticket_bug` | `relatedTicketId` | 相关工单 ID，便于复现和定位 |

其余分类无强制 ext 字段；`--ext` 可省略。

### 附件上传说明

用户上传的截图、日志等文件，脚本内部会在建单前自动先将每个附件 POST 到上传端点取得 URL，再随建单请求一并提交，整个过程对 agent 透明。调用方式：

```bash
--attachment <沙箱内文件路径>
```

- 每个 `--attachment` 指定一个文件，可重复使用以上传多个文件。
- 正文里只写图片说明；真实截图、日志等文件通过 `--attachment` 上传。

### 问题描述：准确、精准地整理

`--content` 不是简单复制用户某一句话，而是结合整段对话上下文，**站在用户立场**重新整理，准确表达用户当前真正的诉求：

- **准确、精准、客观**：用专业清晰的描述表达问题，不要太口语化、情绪化或闲聊化；可以保留必要的第一人称，但不要写成第三人称客服转述（不要"该用户反馈……"）。
- **整合上下文**：把多轮对话里零散的信息（现象、已尝试的操作、期望结果、实际结果、相关 ID/截图说明）汇总成一段完整、自洽的描述。
- **准确不夸大**：只写对话里真实出现的信息，不要替用户编造未确认的细节、原因或诉求；用户表达模糊时如实保留，不要脑补。
- **聚焦真实诉求**：先点明用户现在最想解决/想要的是什么，再补背景，避免被中间的闲聊带偏。

### 创建前必须先确认（强制）

整理好工单明细后，**先把明细完整列给用户确认，得到明确同意才调用 `create-ticket`**。不要跳过确认直接创建。

向用户展示的明细至少包含：

```text
即将为你创建售后工单，请确认以下内容：

- 问题描述：<以用户口吻整理后的完整描述>
- 问题分类：<分类中文名>
- 扩展字段：<如 chatId、relatedTicketId 等，无则省略>
- 附件：<文件名列表，无则省略>
- 工单标题：<subject，可选>
- 联系邮箱：<contactEmail，可选>

确认无误我就提交；需要修改的话告诉我要改哪里。
```

- 用户确认后再执行 `create-ticket`，并把确认后的描述作为 `--content`。
- 用户要求修改时，按反馈改完重新展示明细，再次确认后才提交。
- 用户没有明确确认前，不要调用创建接口。

创建后必须根据接口返回的 `status` 判断结果，并且只向用户展示客户可见工单号 `ticketNumber`。不要向用户解释"本地工单""同步""Tars""内部客服系统"等实现细节：

- `status == "created"`：明确告知工单创建成功，给出工单号，并把工单号渲染成可点击的 Markdown 链接，链接使用脚本返回的 `ticketDetailUrl`；同时按下方话术规范给出预估跟进时效与后续方式。
- `status == "syncing"`：说明已收到并正在受理工单，可给工单号；同样把工单号渲染成可点击的 Markdown 链接，链接使用脚本返回的 `ticketDetailUrl`；用"正在受理"措辞，不要承诺客服已接单，跟进时效可照常给出。
- `status == "sync_failed"`：说明工单暂时提交失败，致歉并建议稍后重试或联系 Shulex 客服；不要说"创建成功"，也不要给跟进时效承诺。
- `tarsTicketNumber` / `shulexTicketNumber` 是内部字段，不能展示给用户，不能拿它替代 `ticketNumber`。

### 售后客服话术规范（创建成功后）

用专业、有温度的售后客服语气回复，包含以下要素（按需裁剪，不要机械堆砌）：

1. **确认受理 + 适度共情**：先告诉用户问题已收到、工单已建好；若用户明显受困扰，简短致歉（"给你带来不便很抱歉"），不要过度道歉。
2. **工单号**：先直接展示 `ticketNumber`，再用脚本返回的 `ticketDetailUrl` 拼出“工单详情页”的 Markdown 链接，方便后续追踪。
3. **预估时效**：给出明确的跟进时效，默认 **售后团队会在 2–5 个工作日内跟进处理（节假日顺延）**；可按紧急度调整措辞（严重问题会优先处理），但**只承诺"跟进 / 回复"的时效，不承诺具体解决时间或结果**。
4. **后续跟进方式**：说明会有售后人员跟进；用户可凭工单号在「售后工单」列表查看进度、随时把工单号发给我继续补充信息 / 上传截图日志；若填写了联系邮箱，进展也会通过邮件通知。
5. **礼貌收尾**：感谢用户的耐心与反馈。

约束：

- 不透露任何内部实现（Tars、本地工单、同步、内部客服系统等）。
- 不编造未发生的事（如"客服已接单""预计今天解决"）；时效只说预估，不打包票。
- 时效与 `status` 匹配：仅 `created` / `syncing` 给跟进时效；`sync_failed` 不给时效，改为致歉 + 重试 / 联系客服建议。

成功话术示例：

```text
你好，你的售后工单已经创建好了。

工单号：CX-1
你可以点击跳转至[工单详情页](https://ai-staging.solvea.cx/chatbot#/support/tickets/CX-1)查看此工单进展，建议留存方便后续追踪。

我们已经收到你反馈的问题，售后团队会在 2–5 个工作日内跟进处理（节假日顺延），有进展会第一时间同步给你。处理期间你可以：
- 在「售后工单」列表凭工单号查看最新进度；
- 直接把工单号发给我，继续补充信息或上传截图 / 日志，我会同步到这条工单；
- 若你留了联系邮箱，后续进展也会通过邮件通知你。

给你带来不便很抱歉，感谢你的耐心与反馈！
```

## 查询与追加

- 查询时回答当前状态、最新一条人工回复、下一步建议。
- 追加时先确认目标工单号，再把用户的新描述作为客户补充消息追加到该工单。
- 如果用户在当前对话里直接问"我那个工单怎么样了"，但没有可定位的工单号，先让用户提供工单号。
