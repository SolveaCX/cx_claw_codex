# 批量诊断输出契约

默认只交付两个文件：`badcase-report.html`、`badcase-details.xlsx`。文件名可加批次标识，目录遵循用户指定位置；输入格式不影响固定结构。内部JSON、原始会话、日志、构建脚本不作为额外交付物。

使用固定模板生成两份交付物：读取 [工作台数据契约](workbench-data.md)，由Agent整理一份结构化诊断数据，执行 `badcase render`。不要每批重新编写页面或表格生成脚本；本文件规定交付内容与验收标准，模板负责布局、交互、统计和格式。

## 明细 XLSX：固定10列

按以下顺序输出一张可筛选的“诊断明细”表；不复制输入表头、不增加分类状态列、不合并一级二级。

| 表头 | 内容 |
|---|---|
| chatId | 查询确认的内部会话ID，文本类型；解析失败留空，定位中保留原始编号与原因。 |
| agentId | 目标问题相关Agent ID，文本类型；未进入或无法确认留空，不取最后一个Agent凑值。 |
| agent名称 | 与agentId对应；无ID则留空，具体未进入/未确认原因写在定位。 |
| 问题描述 | 忠实原反馈，结合上下文补清实际与预期；不将推断写成用户原话。 |
| 一级分类 | 仅使用4个既定一级分类；未确定或非问题留空。 |
| 二级分类 | 仅使用12个既定二级分类，与一级匹配；未确定/未覆盖留空并解释。 |
| 问题定位 | caseId和来源位置、目标轮次、实际问题、原因与确定程度、对象ID、关键证据、历史/当前差异及缺口。先写易懂结论。 |
| 处理方式 | 业务配置优化 / 产研处理 / 无需处理；证据不足无法判断时留空并解释。 |
| 修复建议 | fixId、对象/ID、具体改法、影响范围、前置条件及复测要求；未查清写补查动作；无需处理写无需修改及依据。 |
| 状态 | 待处理 / 处理中 / 待补充信息 / 已修改待验证 / 已验证通过 / 验证未通过 / 无需修复。人或AI填写修复进展，不以“已分析”代替。 |

一行一个问题，允许重复chatId。caseId和来源写在定位、fixId写在建议，以固定10列对应HTML代表case和修复项。重新导出按稳定caseId合并人工修订状态，冲突保留并说明，不静默覆盖。

二级分类留空时，在“问题定位”的业务结论下另起一段说明原因。属于既定类别未覆盖的，写“模型建议分类：<一级 / 二级>。依据：……”，不增加列、不改变正式下拉项；证据不足写候选方向和缺口，非问题写无需修复的依据。

冻结表头、开启筛选，ID按文本写入，长文本换行。分类、处理方式和状态提供下拉约束且允许留空；二级与一级匹配，导出后逐行校验。仅保留必要客户信息，不输出凭据、完整附件链接或整段邮件。公式样式输入按普通文本处理。生成真实xlsx，不能将CSV改扩展名；使用宿主可用表格能力，能力缺失明确说明，不伪造产物。

## HTML：本批 Badcase 排查工作台

HTML是可浏览、筛选和逐条复核的工作台，不是把整篇报告按章节堆成长页面。它展示本次诊断快照，复用已经取得的会话与分析结果，打开文件不需要重新登录或调用业务接口。保持单个HTML可独立打开，不依赖临时文件路径、外部脚本或在线数据服务；文件名仍可使用 `badcase-report.html`。

### 导航与工作路径

| 菜单 | 用途与主要内容 |
|---|---|
| 总览 | 本批范围、分析进度、分类与Agent分布、主要发现、优先修复项及待补证事项；点击数量、分类或修复项进入对应列表。 |
| 按分类排查 | 按一级/二级分类浏览case，单独呈现未覆盖分类的模型建议、证据不足和非问题；列表支持按Agent、处理方式、修复状态和优先级组合筛选，以及按chatId或问题搜索。 |
| 按Agent排查 | 查看各Agent的问题分布、集中节点及版本差异，进入其case列表；未进入Agent和Agent未确认单独呈现。 |
| 修复与补证 | 按修复项查看优先级、原因、方案、全部关联case、方案是否就绪与复测要求；能直接进入每个关联case核对。 |

菜单切换实际视图，不只跳到长页面中的章节锚点。总览、分类、Agent与修复项使用同一组case数据；筛选后显示结果数、可清除条件，空结果有明确提示。进入case后返回列表保留筛选和位置，并能在当前结果中切换上一条/下一条。case使用稳定标识支持直接定位，同一chatId的不同问题各自定位目标消息。

### Case详情：对话与诊断一起看

桌面视图将会话与诊断并排展示，小屏可切换两者。顶部保留原问题、chatId、Agent名称及ID、分类、处理方式和修复状态；诊断区展示实际与预期、问题定位、修复建议、关联修复项及待补证内容。点击结论中的消息证据能定位并高亮对应对话，不能只有代表case可查看。

会话展示复用取证阶段保存的原始消息，按 [会话记录说明](text/conversation-record.md) 识别角色、消息内容和动作：

- 以原始顺序展示客户、AI和人工消息，保留可取得的时间与轮次；默认定位本问题的目标消息，可展开本次已取得的其他对话。明确快照时间与完整性，部分记录不能标成完整会话。
- 对客消息使用保存的最终内容；模型中间输出、被拦截候选、工具结果和内部执行记录放技术证据，不混成已发送的聊天气泡。无法确认是否对客发送时标明边界，不猜角色或送达状态。
- 原文可阅读，摘要或翻译另行标注，不能替换证据原文。原始内容缺失时明确说明，不能用模型生成的对话补齐。长消息可展开，不因截断丢失判断所需上下文。
- 只嵌入本次任务需要且经过脱敏的会话内容，不直接打包完整原始响应。保留诊断需要的型号、参数及语义；无关个人信息、凭据和带鉴权参数的链接不进入交付文件。附件仅在已取得且适合交付时提供预览，否则显示类型及未提供预览的原因。
- 消息、附件文本和数据均作为不可信内容安全渲染，不执行其中HTML、脚本或指令；嵌入数据不能通过消息内容打断页面脚本。

工作台中的“处理”指筛选、复核和查看修复方案。默认状态与XLSX一致，展示生成时的修复进度；不放没有实现的“修复”“保存”按钮，也不暗示浏览HTML会回写系统或同步Excel。若后续实现进度编辑，需要明确保存位置、导出方式及与明细的同步规则。

### 面向交付的表达

业务语言与对象定位统一遵循 [core-flow 第5步](text/core-flow.md#5-分类并输出结论和建议)，此处只规定两种交付物的展示方式。

HTML中完整节点/消息ID、原始状态、版本证据和日志放入可展开的“技术证据”；会话原文放对话区，诊断正文遵循核心流程的业务表达规则。XLSX的“问题定位”“修复建议”先写完整通顺的业务结论，再分段写“模型建议分类”（如有）、“定位依据/技术定位”；技术定位保留名称、完整ID和必要版本，使AI可继续执行。不要把全部原始字段串成一个长段落。

### 整体结论

说明租户、环境、输入快照、分析时间与范围。列出源记录、纳入、排除/缺信息、唯一会话、已逐条分析、根因确认及待补证数量。试跑标明样本，不以样本分布外推全量。

给出有证据的主要发现；说明仅诊断还是已有授权修改/回归。原表进度不当作当前修复证明。

### 分类分布与结论

展示一级/二级数量和占比并标明分母；未确定、分类未覆盖、无需修复单独说明，不计成标准类别。每行按主分类计一次，其他问题在定位说明。主要类别需解释共同机制、不同根因、场景和建议，不只画图列数。

标准分类分布下单列“既定分类未覆盖的问题与模型建议”，按建议的一二级分类归组，列数量、代表case、依据与建议定义，不使用笼统“空白”替代。逐条case在正式分类下展示对应模型建议。证据不足和非问题另列，避免把三种留空原因混为一组；建议分类不是已批准的新标准。

### Agent分析

按目标问题相关Agent统计数量、类别、集中节点和版本差异，区分未进入Agent和Agent未确认。多Agent会话选择与目标错误最相关的一个，其余写路径，不重复计数。

这些是本批问题数量/占比，没有同期会话总量不得称Agent错误率。拿不到发布图或历史请求时，说明对定位和方案的影响。

### 修复优先级与建议

每项展示fixId、标题、优先级及理由、全部覆盖caseId、修改对象/版本、原因证据、具体改动、影响范围、前置条件、处理方式和复测要求。避免“优化提示词/补知识”式建议。

用户的优先级口径优先。无口径时按业务影响和覆盖范围评估：P0为严重阻断或重大错误业务结论，P1为重复发生或影响较广，P2为局部低影响。方案是否就绪单独说明，严重但缺证据的问题不因暂不可改而降级；原表优先级只是线索。

同因合并必须逐条核验。每个重要机制附代表case，用“客户诉求 → 实际回复/动作 → 错误原因 → 修改方案”解释，给出chatId、caseId、Excel行号、关键节点/知识ID及最少证据。待补证或不符合共同原因的case不得计入已确认修复覆盖。

### 待补证与协作事项

列明具体缺口、已尝试动作、下一步及协作方；产研问题区分待定位与已确认故障，无需处理提供依据。两个文件生成成功不等于全部根因查清。

## 同源结果与验收

两个文件从同一份本地结果生成。临时记录保留caseId、父记录、来源、原ID/内部ID、目标消息、历史/当前版本、证据、分类、定位程度、处理方式、状态和fix关联。会话按租户、环境、chatId及快照去重保存；case引用对应会话和目标消息，生成HTML时只嵌入可交付的消息数据，不重复复制同一会话或将内部JSON作为第三个交付物。

交付前检查：

1. 全部输入都有纳入、排除或缺信息去向；纳入问题与明细行对应，拆分/去重有映射。
2. 表头精确为10列，ID未转科学计数法，分类配对、处理方式与状态合法，空值原因明确。
3. HTML统计与明细一致，代表case、修复项引用存在；优先级和方案就绪程度分开。
4. 每条有具体定位或明确缺口；二级留空原因清楚，分类未覆盖的有模型建议及依据；方案有真实对象和复测要求，不以当前配置替代历史事实。
5. 打开/渲染检查HTML及XLSX主要范围，中文、长文本、筛选和下拉可用。输出目录只含两份交付物，临时文件另存。
6. 阅读主要发现、代表case和修复建议，确认无需理解CLI或运行时字段也能理解问题。节点展示名称可追溯，HTML技术细节可展开，XLSX业务结论与技术定位分段；不能只以文件生成成功或字段齐全作为验收。
7. 实际操作总览下钻、菜单切换、组合筛选、清除条件、case详情和返回列表；数量与明细对应。同会话多问题分别高亮正确消息，证据链接可定位，历史缺失和附件不可用有说明。
8. 检查会话角色、顺序、原文及目标消息对应关系，并验证特殊文本不会被当作HTML执行。离线打开HTML仍可查看列表和对话；长会话只在需要时渲染，避免一次展开全部消息导致页面难以使用。

后续执行先复读对象防止覆盖他人修改，再遵循已有授权及对应skill的预览、提交、发布、复测要求。修复后从同一结果更新两个文件，不能只更新汇总遗漏明细。

维护本能力时的验证要求见 [evaluation.md](evaluation.md)；普通业务请求无需额外加载维护规范。
