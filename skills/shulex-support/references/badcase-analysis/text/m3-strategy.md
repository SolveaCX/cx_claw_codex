# M3：策略匹配排查

M3 负责确认已经得到的意图和变量值如何命中策略，以及命中后选择了什么动作。先对齐会话里实际使用的输入、策略和动作，再读取当前策略配置逐条比较。

---

## 边界

M3 只处理意图识别完成之后、Agent 或回复动作执行之前的问题：

- 有候选意图但没有策略命中。
- 命中了非预期策略，或更宽泛的策略提前命中。
- 策略条件引用的意图、触点或变量值与会话事实不匹配。
- 策略命中正确，但配置的动作类型或目标对象不符合预期。
- 请求显式指定策略或 Agent，导致常规策略匹配被绕过。

用户意图本身识别错误时回 M2；策略依赖的变量系统字段缺失或值错时转 M4；策略已正确路由到 Agent 后的执行问题转 M5，CHAT_FLOW 内部问题转 M10。

---

## 排查顺序

### 1. 对齐会话记录中的目标事实

| 字段 | 要回答的问题 |
|------|--------------|
| `context.intents[]/intent` | 策略实际拿到的意图结果是什么 |
| `context.metadata.ai_fields` 及相关 metadata | 条件依赖的实际值是什么，字段是否存在、为空或类型不同 |
| `context.strategyId/strategyName` | 当轮最终记录了哪条策略；为空时是否最终进入 `CONFUSED/NOTHING` |
| `context.strategyAction` | 命中后选择了回复、模板、转人工、不处理还是 Agent |
| 回复 `type/handoff/reason/reasonDesc` | 策略动作最终表现成什么用户可见结果 |
| `contextComparison.strategyAction` | 当前策略动作是什么，只用于与历史结果比较 |
| `contextComparison.contextModifiedList` | 历史使用的策略是否后来被修改或删除 |

先形成一条最短链路：

```text
意图与条件实际值 -> strategyId / strategyName -> strategyAction -> 最终回复类型
```

不要用 `originIntent` 代替策略输入。策略消费的是配置意图 ID、触点及 metadata 等条件值；`originIntent != intent` 也不是策略过滤意图的证据。

### 2. 读取当前配置

```bash
cxclawctl api list-strategies --pretty
```

先按 `strategyId` 定位当轮实际策略，再找业务上预期命中的策略。条件字段含义不明确时读取：

```bash
cxclawctl api list-entities --pretty
```

比较以下内容：

- `status/trigger`：策略是否启用，是否处理消息触发。
- `rank`：策略匹配有先后顺序；先满足条件的策略会阻止后续策略继续匹配。
- `condition`：逐条记录 `apiName/apiType/relation/values`，不要只复述整段 JSON。
- 实际值：从目标轮次 `intents[]`、触点和 metadata 中找到每条条件对应的值。
- `action`：动作类型及关联的 Agent、模板、知识目录或转人工配置是否符合预期。

对实际策略和预期策略都做同样比较。只证明“预期策略条件满足”还不够，还要确认是否有更靠前的策略也满足。

### 3. 结合字段值判断

对每条关键条件写清楚：

```text
条件字段 -> 会话实际值 -> 策略期望值 -> relation -> 是否应匹配
```

| 会话事实 | 判断 |
|----------|------|
| `intents[]` 已错误 | 策略只是消费了错误输入，主根因在 M2 |
| `intents[]` 正确，`strategyName` 为空，回复为 `CONFUSED` | 检查预期策略状态、顺序和每条条件，不要说“意图没识别到” |
| 命中非预期 `strategyName` | 先验证该策略为何满足，再检查它是否排在预期策略之前 |
| 策略条件引用的变量系统字段缺失或为空 | M3 记录条件未满足，字段为什么为空转 M4 |
| 实际值与期望值文本相同但类型不同 | 仍可能不匹配；按 `apiType` 和实际 JSON 类型比较 |
| `strategyName` 正确但 `strategyAction` 不符合业务预期 | 属于策略动作配置问题；再对照最终回复类型确认影响 |
| `strategyAction` 正确路由到 Agent，但 Agent 内部走错 | M3 已完成，转 M5；CHAT_FLOW 节点问题转 M10 |
| 当前配置无法解释当轮 `strategyId` | 查历史修改信息；仍无法解释时考虑显式指定或历史版本，不能直接断言系统随机路由 |

`__intent_ids` 等 ID 条件按数字比较；不要把字符串形式的 ID 当作等价配置。数组、多选值和嵌套字段要同时核对 relation 语义，不能只看“列表里好像包含”。

### 4. 最后才查日志

第一版诊断默认不查日志。只有以下问题在会话事实和当前策略配置中仍无法回答时，才读取 `sls-query.md`：

- 无法确认当轮是否走了常规策略匹配，还是显式指定策略或 Agent。
- 需要证明多条策略的实际检查顺序和第一条命中项。
- 会话记录只有“未命中”，但无法确认具体哪条条件失败。
- 当前策略与历史 `strategyId/strategyAction` 矛盾，且没有修改记录可解释。

日志只补齐当轮匹配事实。没有日志时，列出尚未确认的条件或历史版本，不要猜测内部执行路径。

---

## 历史与当前状态边界

- `context.strategyId/strategyName/strategyAction` 是当轮保存的执行结果。
- `list-strategies/list-entities` 是当前配置，适合解释现在的条件、顺序和动作。
- `contextComparison.strategyAction` 不是当轮动作；它用于展示当前资源状态。
- 策略后来被改过时，当前条件不能用于证明历史为什么命中或未命中。

---

## 常见根因与建议

| 根因 | 建议 |
|------|------|
| 正确意图没有对应启用策略 | `[可自行调整]` 为意图补充策略并确认动作 |
| 条件字段缺失或实际值为空 | 先转 M4 判断字段来源，再决定改字段还是放宽条件 |
| 实际值与条件值类型不一致 | `[可自行调整]` 统一字段类型和条件值格式 |
| 宽泛策略排在前面先命中 | `[可自行调整]` 收紧宽泛条件或调整策略顺序 |
| 策略命中正确但动作配置错误 | `[可自行调整]` 修改该策略的 action 目标，不要调整意图掩盖问题 |
| 当前配置无法解释历史结果 | `[需联系研发]` 提供当轮策略字段和当前配置差异，继续确认历史版本或指定路由 |

---

## 报告口径

- 必须写出实际策略和预期策略的 ID / 名称、关键条件、实际值、期望值和顺序。
- 先解释为什么命中或未命中，再说明动作造成的用户影响。
- 不要把 `originIntent` 与 `intent` 的差异描述成策略修改了意图。
- 字段值错误时，M3 只说明它如何影响条件；字段为什么错误交给 M4。
