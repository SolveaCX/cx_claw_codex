# M2：意图识别排查

M2 负责确认用户表达经过查询整理后，被识别成了什么意图，以及这个结果是否符合当前意图配置。先还原目标轮次的事实，再读取相关意图；不要从最终命中的策略或回复倒推意图识别一定正确。

---

## 边界

M2 只处理进入策略匹配之前的问题：

- 用户原话经过整理或翻译后语义发生偏移。
- 原始识别意图与用户核心诉求不一致。
- 原始识别结果映射到项目意图后出现偏差。
- 正确意图不存在、未启用，或描述边界与相邻意图重叠。
- 多个候选意图的选择不符合业务预期。

如果 `intents[]` 已包含预期意图，但策略为空、命中错误或动作错误，进入 M3；不要继续把策略问题归到 M2。

---

## 排查顺序

### 1. 对齐会话记录中的目标事实

只读取目标用户消息、对应回复和必要的前置轮次：

| 字段 | 要回答的问题 |
|------|--------------|
| 用户消息 `content`，以及邮件的 `subject/snippet` | 用户真正的主诉是什么；订单号、产品名等背景词是否掩盖了核心动作 |
| `context.mixedQuery.userQuery/userEnQuery` | 整理或翻译后的问题是否仍保持原意 |
| `context.originIntent` | 当轮保存的原始识别名称是什么 |
| `context.intents[]` | 实际落到项目配置中的候选意图有哪些，顺序如何 |
| `context.intent` | 兼容字段中的最终意图；通常与 `intents[0].name` 对齐 |
| 回复 `type` | 是正常进入后续处理，还是 `CONFUSED` 等未完成路由状态 |
| `contextComparison.contextModifiedList` | 相关意图是否在会话发生后被修改或删除 |

按下面的顺序形成事实链：

1. 用一句话概括用户核心诉求，不直接复用系统生成的摘要。
2. 对比原话与 `mixedQuery`，确认偏差是否在识别前已经出现。
3. 对比 `originIntent`、`intents[]` 和 `intent`，指出偏差发生在原始识别还是配置意图映射。
4. 再看策略字段；只有意图结果已正确时才转 M3。

`originIntent` 与 `intent` 不同，不代表策略把意图过滤或改写了。它们分别是原始识别名称和项目配置中的结果，差异本身只是一条待解释的映射信号。

### 2. 读取当前配置

```bash
$HOME/.codex/cxclaw/bin/cxclaw-launcher api list-intents --pretty
```

先按 ID / 名称找到当轮实际意图和用户预期意图；需要确认单个意图完整信息时再执行：

```bash
$HOME/.codex/cxclaw/bin/cxclaw-launcher api get-intent --id <intent_id> --pretty
```

逐项比较：

- `status`：实际意图和预期意图是否启用。
- `description`：是否覆盖用户这类表达，并明确适用范围与排除边界；`get-intent` 详情中的对应字段名是 `example`。
- 相邻意图：名称或描述是否同时覆盖“对象相同、动作不同”的混合表达。
- 重复配置：是否存在同名、近义或新旧两套意图，状态和用途不同。

不要只看名称判断语义，也不要批量扫完所有意图后笼统说“模型区分能力不足”。报告必须引用与本条问题直接相关的实际意图、预期意图及其描述差异。

### 3. 结合字段值判断

| 会话事实 | 判断 |
|----------|------|
| `mixedQuery` 已改变用户核心诉求 | 偏差发生在识别前的问题整理；不能仅靠修改意图描述解释 |
| `originIntent` 已经与用户诉求不符 | 原始识别错误；再用当前相关意图描述判断是覆盖不足、边界重叠，还是仍缺历史证据 |
| `originIntent` 合理，但 `intents[]/intent` 落到另一配置意图 | 关注名称映射、可用意图集合或覆盖结果；不要归因到策略条件 |
| `intents[]` 含预期意图，但第一项不是预期结果 | 记录候选顺序；当前配置只能解释语义边界，不能证明当时的排序原因 |
| `intents[]` 正确，但 `strategyName` 为空或错误 | M2 已完成，转 M3 |
| `originIntent` 为空、`intents[]` 非空 | 只能确认保存结果不完整或存在兜底/覆盖，不能直接断言“没有执行识别” |
| `type=CONFUSED` 且 `intents[]` 非空 | 意图已有结果但后续未完成路由，优先转 M3 |
| 当前预期意图为 `DISABLED` | 说明当前不可命中；只有历史变更证据能证明当时也是该状态 |

### 4. 最后才查日志

第一版诊断默认停在会话事实和当前配置。只有以下问题仍无法回答时，才读取 `sls-query.md` 做聚焦查询：

- 无法确认当轮使用的是正常识别、上轮复用、指定意图还是兜底结果。
- 需要证明当轮实际送入识别的候选意图和描述。
- 需要确认原始识别结果、候选顺序或下游返回是否为空。
- 会话记录与当前配置明显矛盾，且没有历史变更信息。

需要继续判断算法请求和返回时转 M11。没有日志证据时，把这些内容写成“待确认”，不要用当前配置补成历史事实。

---

## 历史与当前状态边界

- `messages[].context` 是当轮保存的结果，优先作为历史事实。
- `list-intents/get-intent` 读取的是当前配置，只能解释现在的状态和语义边界。
- `contextComparison` 是当前资源与历史记录的比较，不是重新执行意图识别。
- 当前描述更合理，不代表当轮模型一定见过同一版本；当前描述不合理，也不能单独证明它就是历史误判原因。

---

## 常见根因与建议

| 根因 | 建议 |
|------|------|
| 用户核心诉求在 `mixedQuery` 中被改写偏 | `[需联系研发]` 提供原话与改写结果，继续定位问题整理环节 |
| 正确意图当前未启用 | `[可自行调整]` 确认业务范围后启用，并补齐对应策略 |
| 意图描述覆盖不足 | `[可自行调整]` 增加真实表达和适用边界，不只堆关键词 |
| 相邻意图描述重叠 | `[可自行调整]` 同时补充正向范围和排除条件，区分对象与用户动作 |
| 原始识别正确但配置意图结果异常 | `[需联系研发]` 提供 `originIntent`、`intents[]` 和相关意图 ID，继续确认映射过程 |
| 意图结果正确但没有进入预期策略 | 转 M3，不修改意图来掩盖策略配置问题 |

---

## 报告口径

- 先说用户主诉、`mixedQuery`、`originIntent`、`intents[]` 分别是什么，再说偏差发生在哪一步。
- 引用实际意图和预期意图的当前状态与描述；描述读取失败时明确写“配置未确认”。
- 不要把 `originIntent != intent` 写成策略阶段修改了意图。
- 没有历史版本或日志时，不要断言当前意图描述就是当轮误判根因。
