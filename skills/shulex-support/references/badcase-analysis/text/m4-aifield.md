# M4：变量系统字段排查

M4 负责确认目标轮次实际携带了哪些变量系统字段、字段值是否符合用户表达和当前配置，以及错误值如何影响策略、Agent、工具或 CHAT_FLOW。先判断目标字段是否真的参与了本次异常，再分析字段本身。

---

## 边界

M4 处理 Agent 执行前已经形成的变量系统字段问题：

- 业务需要的字段在 `metadata.ai_fields` 中缺失、为空或值错误。
- 字段值类型、父子结构或多值形式与下游预期不一致。
- 当前字段配置的描述、状态、数据类型或应用范围不适合目标场景。
- 上游已有值与当轮重新抽取结果之间可能发生覆盖。
- 字段正确，但策略、工具或节点引用了错误字段。

如果字段值正确而策略条件仍未命中，转 M3；字段值正确而工具参数为空，转 M6；CHAT_FLOW 内部赋值或覆盖问题转 M10。

---

## 排查顺序

### 1. 对齐会话记录中的目标事实

先从用户描述和异常结果反推“哪个变量系统字段可能影响了结果”，不要无差别检查全部字段。

| 字段 | 要回答的问题 |
|------|--------------|
| 用户消息、必要前置轮次和附件 | 用户是否真实提供了目标信息，值是什么，是否有多个互相冲突的值 |
| `context.metadata.ai_fields` | 当轮后续环节实际拿到哪些字段 |
| `ai_fields[].id/name` | 当前结果对应哪个变量系统字段，避免只按相似名称猜测 |
| `ai_fields[].value/values` | 单值兼容字段与多值结果分别是什么；下游实际需要哪种形态 |
| `ai_fields[].dataType/bizType` | 值的类型和业务类别是否符合下游用途 |
| `ai_fields[].children` | 订单等父字段的目标值是否实际位于子字段中 |
| `ai_fields[].aiExtract` | 该结果是否标记为 AI 抽取；不能仅凭此字段还原完整调用方 |
| 策略条件、工具参数或 ChatFlow 变量引用 | 目标字段是否真的被异常路径消费 |

`metadata.ai_fields` 通常是字段对象列表，不要把它想当然地当成 `ai_fields.xxx` 平铺字典。按 ID / 名称找到目标对象，再检查 `value`、`values` 和 `children`。

先形成一条最短影响链：

```text
用户提供的信息 -> ai_fields 中的目标对象和值 -> 下游引用位置 -> 异常结果
```

目标字段没有被下游引用时，即使值为空也通常不是本次 badcase 根因。

### 2. 读取当前配置

```bash
cxclawctl api list-ai-fields --pretty
```

按会话中的字段 ID / 名称定位当前配置，比较：

- `state`：字段当前是否启用。
- `description`：说明是否明确要从什么表达中提取什么值。
- `dataType`：字符串、日期、下拉等类型是否和会话值及下游条件一致。
- `applyRang`：字段是否覆盖策略、Agent、模板或其它实际使用范围。
- `parentId/children`：目标是父级业务对象还是具体子字段。
- 可选值配置：分类或下拉字段的允许值是否覆盖本次表达。

当前配置只说明现在应该怎样抽取和使用。不要因为当前字段存在，就断言当轮一定加载了它；也不要因为当前字段被关闭，就断言当轮没有抽取。

### 3. 结合字段值判断

| 会话事实 | 判断 |
|----------|------|
| 用户没有提供目标信息，字段值为空 | 通常是正常结果；检查下游是否不合理地把它设为必需条件 |
| 用户明确提供了信息，但目标字段对象不存在 | 可能是当轮未加载该字段、应用范围不覆盖或结果未保存；当前配置不足以单独定因 |
| 字段对象存在，但 `value/values` 为空 | 确认描述、类型、父子位置和用户表达；只能确认没有得到有效值，不能直接断言某个服务失败 |
| `value` 与 `values[0]` 不一致 | 记录下游实际消费的形态；不要任选一个值作为正确结果 |
| 父字段为空，但 `children` 中目标子字段有值 | 不能判定整体抽取失败；按下游引用的具体字段判断 |
| 字段值正确但 JSON 类型与策略条件不同 | 字段抽取可能正确，影响点在类型契约；转 M3 核对条件 |
| 字段值正确但工具参数为空 | 转 M6 核对参数来源和字段映射 |
| 字段在 CHAT_FLOW 中被再次赋值或覆盖 | 转 M10，对齐节点执行记录和变量覆盖结果 |
| 当前字段配置与会话结果不一致 | 先看 `contextComparison` 或修改时间；没有历史证据时只报告当前差异 |

多轮会话中，目标值可能来自前置轮次，也可能被新值覆盖。必须读取影响当前结果的最少前置轮次，不能只看最后一句是否出现该值。

### 4. 最后才查日志

第一版诊断默认不查日志。只有以下问题仍无法由会话事实和当前配置解释时，才读取 `sls-query.md`：

- 需要确认字段是随请求传入、沿用历史值，还是当轮重新抽取。
- 用户明确提供了值，但会话记录无法说明字段为何缺失或被覆盖。
- 需要确认实际加载了哪些字段、输入文本或附件，以及返回的原始字段结果。
- 会话记录与当前字段配置冲突，且没有历史变更信息。

若后续证据表明是字段抽取内部异常，再进入对应服务或 M11。没有日志时，不要从“没看到某段调用”推断它一定没有发生。

---

## 历史与当前状态边界

- `context.metadata.ai_fields` 是当轮后续环节实际保存和消费的字段结果，优先作为历史事实。
- `list-ai-fields` 返回当前字段定义，不是当轮加载字段的快照。
- 当前描述、类型、状态或应用范围发生变化时，只能说明现在的配置不同。
- `contextComparison` 可以提示资源变化，但不会重新抽取字段。

---

## 常见根因与建议

| 根因 | 建议 |
|------|------|
| 用户没有提供字段值，但策略强依赖该字段 | `[可自行调整]` 增加兜底条件或在进入该路径前收集信息 |
| 字段描述未覆盖真实表达 | `[可自行调整]` 明确提取对象、典型表达和期望值示例 |
| 字段类型与策略条件不一致 | `[可自行调整]` 统一字段数据类型和条件值格式 |
| 父子字段引用错误 | `[可自行调整]` 让下游引用实际承载值的子字段 |
| 字段值正确但策略或工具未使用 | 转 M3 / M6 修正引用，不重复修改抽取配置 |
| 用户提供值但当轮字段仍缺失，且当前配置无法解释 | `[需联系研发]` 提供目标字段 ID、用户原话和会话中的 `ai_fields` 结果继续定位 |

---

## 报告口径

- 先写目标字段为什么与本次异常有关，再写用户原话、字段对象和值、下游引用位置。
- 区分“字段对象不存在”“字段存在但为空”“字段值错误”“字段正确但未被消费”。
- 配置问题标明当前字段 ID / 名称、类型和应用范围；不要只说“实体提取失败”。
- 未进入日志阶段时，不要写具体调用方或服务异常作为确定根因。
