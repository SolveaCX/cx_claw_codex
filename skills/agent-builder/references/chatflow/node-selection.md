# Chatflow 节点选择指南

本指南先确定节点职责，再确定节点组合。每个节点应有单一、可验证的输入/输出合同；不要用一个 AGENT 或一段 prompt 包揽分类、收集、调用、回复和转人工。

## 决策顺序

按以下顺序判断，命中确定性条件后停止继续泛化：

1. 固定入口/终点/人工动作：`START`、`FINISH`、`TRANSFER_TO_HUMAN`。
2. 流程必须取得客户输入后才能继续：`QUESTION`。只有流程明确要求客户作出选项选择时才用 `USER_REPLY`；收集字段/附件用 `VARIABLE`。
3. 已有结构化值或工具状态需要判断：优先 `IF_ELSE` 或 `TOOL` 的 `actionStatus` 出边。流程图中的 Y/N 默认是条件结果：Y = 条件满足，N = 条件不满足，不是用户选项。
4. 必须调用外部系统：`TOOL`；工具返回结构复杂时接 `IF_ELSE`，不要让 AGENT 代替确定性状态映射。
5. 只需根据自然语言判断并分配到有限类别：`INTENT`；全局分类规则只在确有跨意图边界/优先级时配置 `prompt`。
6. 知识检索并对客回答：`RAG_REPLY`。
7. 只发送模板、固定话术或生成一段对客回复：`REPLY`；发送后有确定下游时只允许一个 `SOURCE` 出边。
8. 内部抽取/整理/转换：优先 `CODE`（确定性）或 `VARIABLE_PROCESS`（字段抽取/赋值）；需要模型生成内部文本才用 `LLM`。
9. 前述节点都无法表达，且确实需要开放式多轮处理、工具自主选择或由模型决定职责交接时：才使用 `AGENT`。
10. 已确认需要记录业务埋点、且不改变对话或流程语义：使用 `BUSINESS_TRACK`。

如果输入字段、输出分支或等待语义尚未明确，先询问客户是否有节点偏好；若图形无法直接映射，列出候选节点整理方式并询问客户想如何拆分，输出 `open_questions`，不要退化成万能 AGENT。节点参数、资源和运行时 selector 的细节只读最终选中节点的 `nodes/*.md`，不要在本文件重复展开。

## 节点能力、优势与边界

| 节点 | 独立职责/输入                                                                    | 优势                         | 不适用与替代                                            |
|---|----------------------------------------------------------------------------------|------------------------------|---------------------------------------------------------|
| `START` | 启动流程                                                                         | 结构清晰                     | 不放业务逻辑                                            |
| `FINISH` | 正常结束                                                                         | 明确终态                     | 需要人工接管用 TRANSFER                                 |
| `QUESTION` | 流程必须取得客户选择、确认、字段或附件后才能继续；USER_REPLY 产出选项，VARIABLE 产出字段 | 真正暂停、支持 max_rounds    | 不调用工具、不回答知识；只需发送说明用 REPLY |
| `REPLY` | 发送模板、固定话术或生成一段对客回复；存在下游时发送后等待一轮用户消息 | 话术与动作分离 | 不做判断或结构化收集；必须使用客户回复才能继续时改用 QUESTION |
| `TRANSFER_TO_HUMAN` | 可选直接转人工、模型生成话术转人工、模版发送话术转人工，发送后立马执行转人工动作 | 终止语义明确                 |                                                         |
| `INTENT` | 根据自然语言在有限意图和 OTHER 中做一次分类分配，可选配置全局分类 PE | 适合纯语义判断和路由 | 不处理结构化状态、不负责多轮任务；每个意图必须有可解释下游 |
| `IF_ELSE` | 对变量、工具出参或代码结果执行 if/elif/else 路由（多个 cases=if/elif，FALSE=else） | 确定性、可测试 |
| `TOOL` | 调用一个外部工具并暴露结果/status                                                | 外部的http工具 | 不生成解释；工具若有配置状态映射，优先用 actionStatus   |
| `RAG_REPLY` | 检索知识并回答，TRUE/LACK_KNOWLEDGE                                              | 知识问答稳定                 | 不代替确认/工具调用；目录必须真实存在                   |
| `CODE` | 纯确定性字段提取、清洗、归一化、拆分、组装                                           | 可重复、稳定、低成本；适合整理出 IF_ELSE 可判断的值 | 不做模型判断、HTTP、长文本；复杂路由用 IF_ELSE          |
| `VARIABLE_PROCESS` | 从上下文抽取字段和/或写入 SYSTEM                                                 | 变量桥接、字段合同清晰       | 不等待客户；客户补字段用 QUESTION(VARIABLE)             |
| `LLM` | 生成内部摘要/改写/结构化结果                                                     | 适合非确定文本整理           | 不直接回复、不调用工具、不多出口                        |
| `AGENT` | 持续承担局部开放式问题处理：多轮推理、工具自主选择、解释非结构化结果，并在职责结束后按需交接 | 灵活处理无法预先结构化的任务 | 不用于纯分类、必填收集、单次回复或确定流程；next_steps 不是普通执行顺序 |
| `HUMAN_REVIEW` | 内部审批/填写后继续流程                                                          | 审批合同明确                 | 不是客户会话转人工                                      |
| `SUB_GRAPH` | 调用独立 CHAT_FLOW                                                               | 复用子流程                   | 当前后端禁止出边                                        |
| `BUSINESS_TRACK` | 记录确认的业务追踪事件后继续                                                    | 不干扰业务执行               | 不替代工具、回复、判断或用户交互                        |

## AGENT 与 next_steps：准入门禁

AGENT 必须承担一个需要模型持续处理的局部职责，而不是“执行一个简单步骤，然后跳到下一节点”。只有同时满足
以下条件，才为 AGENT 配置 `next_steps`：

1. 当前职责不能由 `INTENT`、`QUESTION`、`REPLY`、`TOOL`、`IF_ELSE`、`LLM` 或其他专用节点直接表达；
2. AGENT 可能在当前节点内多轮回复或自主调用工具；
3. 当前职责结束后确实存在独立的后续业务动作；
4. 由模型根据非结构化上下文决定是否以及何时交接，而不是由固定顺序、工具 status 或结构化字段决定。

只有一个确定下游时使用 AGENT 的 `SOURCE` 出边，不创建单个 `next_steps`。纯判断分配使用 `INTENT`；
必须取得客户信息使用 `QUESTION`；只发送回复使用 `REPLY`；确定工具调用与结果路由使用 `TOOL` / `IF_ELSE`。
不得创建仅表示步骤完成的 `success`、`done`、`continue`、`next` 分支。

迁移或重建现有流程时，来源流程中的 Agent 数量、节点连接和切换指令只是待解释证据，不能直接变成
目标 AGENT 或 `next_steps`。必须先按业务职责重新选型；只有确认保留为模型可选的职责交接，才生成
next step。详细运行语义和配置规则见 `nodes/agent.md`。

## QUESTION 与 REPLY：严格区分

```text
只需向客户发送说明、模板或提醒，不要求把客户下一条回复作为流程输入 → REPLY
流程必须取得客户提供/选择/确认的信息后才能继续 → QUESTION（真正收集并等待） → 后续节点
```

- 先判断需求是“发送一段话”，还是“流程必须得到客户输入”；文案写成问句不代表已经完成收集。
- `QUESTION(USER_REPLY)` 支持多个下游：每个 reply 一条边，并补 `OTHER` 兜底边。
- `QUESTION(VARIABLE)` 只有一个 `SOURCE` 下游；收集完成后再进入后续节点。
- `REPLY` 只有一个确定下游；存在下游时运行时才会等待一轮用户消息，需要按客户回答分支时必须接 QUESTION。

## 状态映射与 AGENT 边界

- 工具 actionStatus 完整、互斥、覆盖分支时：`TOOL → status edges`。
- 读取工具返回字段、变量字段或代码输出时：`TOOL/VARIABLE/CODE → IF_ELSE`；多个 cases 按顺序表达 if/elif，`FALSE` 表达 else；每个 case 和 `FALSE` 都要连边。它只做确定性比较，不做自然语言理解。
- actionStatus 是工具执行后的离散状态，不等于工具普通出参字段。判断状态名用 `tool_status` / `ACTION_STATUS_NAME`；判断返回体字段用 TOOL 出参 path；两者不要混写。
- 自然语言意图才用 `INTENT`；不要用 AGENT 读取布尔/枚举状态再手工选路由。
- 纯自然语言判断并分配到有限类别也使用 `INTENT`，不要仅因为分类需要 LLM 就创建 AGENT。
- 只有需要模型持续综合非结构化信息、自主决定工具调用，或在当前职责完成后决定是否交接到一个或多个明确下游时才用 AGENT。


## 流程图编排前置确认

截图/PDF/白板转 CHAT_FLOW 时，先输出结构化摘要和拟构建 Mermaid，标注入口、节点职责、真实边条件（明确写出 Y=条件满足、N=条件不满足，除非证据表明是用户选择）、等待/收集点、转人工点和不确定区域；用户确认后再写 source、compile、validate。Mermaid 与 graph 不一致时以 graph 为准并立即修正。

## 选择记录与验证

对每个节点记录：`触发输入 → 选择节点 → 输出/等待合同 → 下游边 → 被拒绝的替代节点 → 资源证据`。若存在多个合理节点组合，先询问客户偏好；无法映射的图形节点先列出候选整理方式和 `open_questions`。最终执行 source/资源/edge 对账、compile、validate，并在必要时 replay。
